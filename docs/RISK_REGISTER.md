# ECDAT Risk Register

This document outlines the top risks associated with the ECDAT project, encompassing security, design, and delivery risks. It is intended to be a living document, reviewed and updated by the team during each sprint.

## Top Risks (P0 / P1)

| ID | Risk Description | Likelihood | Impact | Mitigation Strategy |
|----|------------------|------------|--------|---------------------|
| **RSK-01** | **Hand-rolled TLS implementation is incorrect or exploitable**<br>The current network scanner (`ecdat_network_scanner.py`) uses a custom raw TCP/TLS socket handshake instead of a proven library, risking inaccurate protocol detection, missed cipher suites, or vulnerabilities in the scanner itself. | High | High | **Mitigation:** Refactor the network scanner to use `sslyze` (or a similarly robust, maintained TLS analysis library) for all handshake and cipher suite enumeration logic. |
| **RSK-02** | **Regex-only static analysis causes false positives/negatives**<br>Relying solely on regular expressions (`static_scanner.py`) to detect cryptographic assets is brittle, leading to excessive noise (flagging comments or unrelated function calls) or missing critical crypto usage (complex variable assignments or non-standard wrappers). | High | High | **Mitigation:** Introduce AST (Abstract Syntax Tree) parsing or tree-sitter integration for the static scanner to establish context, and utilize the planned LLM verification pass for ambiguous cases. |
| **RSK-03** | **Hardcoded Mosca parameters lead to wrong risk signals**<br>Mosca's theorem variables (`MOSCA_Y=3`, `MOSCA_Z=10`) are currently hardcoded in `merge_and_classify.py`. If these values change based on organizational policy or new NIST timelines, the tool will produce incorrect quantum-readiness assessments without a code change. | Medium | High | **Mitigation:** Externalize classification rules and Mosca parameters into a configurable JSON ruleset, loaded dynamically by the risk engine. |
| **RSK-04** | **Command injection via unvalidated input**<br>The network scanner passes user-supplied hostnames directly into a `subprocess.run(["openssl", "s_client", ...])` call. If input is not strictly validated, an attacker could inject arbitrary shell commands. | Medium | Critical | **Mitigation:** Implement strict input validation (e.g., regex constraints for valid FQDNs/IPs) before passing any user input to shell commands. Alternatively, avoid subprocesses entirely by using native libraries. |
| **RSK-05** | **LLM verification calls leaking sensitive code or secrets**<br>The planned use of an LLM (e.g., Groq) to verify ambiguous static analysis findings risks transmitting proprietary source code or hardcoded secrets to third-party APIs. | High | Critical | **Mitigation:** Implement a strict data-sanitization pipeline before any LLM call to redact string literals, IP addresses, and private key material. Ensure data processing agreements (DPAs) are in place preventing the LLM provider from training on submitted data. |
| **RSK-06** | **Manual CBOM generation leading to schema invalidation**<br>The network scanner currently constructs CycloneDX JSON using raw Python dictionaries. This risks outputting invalid CBOMs that fail to merge or cannot be consumed by other tools. | High | Medium | **Mitigation:** Standardize all scanners to use the official `cyclonedx-python-lib` to ensure schema compliance and consistent model serialization. |
| **RSK-07** | **Lack of automated testing allows regressions**<br>The repository currently lacks unit tests or integration tests. Future changes to regex rules or merge logic may silently break existing functionality. | High | Medium | **Mitigation:** Implement a testing framework (e.g., `pytest`) and create unit tests for all core logic, especially regex parsing and classification rules. Set up CI to block PRs failing tests. |
| **RSK-08** | **No persistent storage results in data loss**<br>Outputs are currently flat JSON and HTML files. If files are overwritten or lost, historical cryptographic posture data and audit trails are lost. | Medium | Medium | **Mitigation:** Implement a database backend (e.g., PostgreSQL) to securely store and version CBOMs and scan results over time. |
| **RSK-09** | **Scalability bottlenecks in the merge engine**<br>As the repository scales to scanning thousands of endpoints and large monorepos, running a synchronous script (`merge_and_classify.py`) locally on a developer's machine will become too slow and memory-intensive. | Medium | Medium | **Mitigation:** Move the merge logic to a scalable backend API and implement asynchronous job queues (e.g., Celery or Redis Queue) for processing large CBOMs. |
| **RSK-10** | **Unauthenticated API access**<br>When the new backend API is developed, failing to secure the endpoints could allow unauthorized users to upload malicious CBOMs or access sensitive cryptographic posture data. | Low | High | **Mitigation:** Design the target architecture API with robust authentication and authorization (e.g., OAuth2, JWT) from day one. |
| **RSK-11** | **Single point of failure in deployment**<br>Relying on manual script execution makes deployment fragile and dependent on local environment configurations (e.g., missing dependencies). | High | Low | **Mitigation:** Containerize all components using Docker and automate deployments via CI/CD pipelines to ensure reproducible environments. |
| **RSK-12** | **Inconsistent finding deduplication**<br>The current merge logic deduplicates based purely on the `bom-ref`. If two scanners generate slightly different `bom-refs` for the exact same underlying asset, it will appear duplicated in the UI. | Medium | Medium | **Mitigation:** Implement a robust identity-matching algorithm in the Risk Engine that evaluates the asset properties (e.g., certificate hash, code location) rather than just trusting the `bom-ref` string. |
